# Безопасность проекта «МедКарта»

Документ описывает модель угроз, принятые меры и то, что осталось сделать.
Обновляйте его при каждом изменении, затрагивающем работу с ключами,
пользовательскими данными или внешними сервисами.

## 1. Секреты

**Правило:** ни один секрет не должен иметь префикс `VITE_`.
Vite подставляет такие переменные прямо в JS-бандл, и они становятся видны
любому посетителю через DevTools → Sources.

| Переменная | Где живёт | Попадает в браузер |
|---|---|---|
| `OPENROUTER_API_KEY` | `.env` на сервере (права 600), локально — `.env` | нет |
| `AI_UPSTREAM_URL`, `AI_MODEL` | там же | нет |
| `PRIVACY_TOKEN_SECRET`, `UPSTASH_*` | там же | нет |
| `ALLOWED_ORIGINS`, `ALLOWED_HOSTS` | там же | нет |

Переменной `VITE_OPENROUTER_API_KEY` в `.env` быть не должно вовсе: сейчас
код её не читает, но любое будущее обращение к ней положит ключ в бандл.
Ключ уходит только по HTTPS (`AI_UPSTREAM_URL` с `http://` допускается лишь
для модели на localhost).

Проверить перед деплоем, что ключа нет в сборке:

```bash
npm run build
grep -R "sk-" dist/ || echo "Секретов в сборке нет"
```

Локально это же прикрыто правилом ESLint `no-restricted-syntax`: обращение к
`import.meta.env.*API_KEY*` из `frontend/src/` считается ошибкой.

## 2. Архитектура обращения к модели

Полное описание — [`docs/privacy-architecture.md`](docs/privacy-architecture.md),
решение и отвергнутые варианты — [ADR 001](docs/adr/001-external-llm-privacy-boundary.md).

```
Браузер ──POST /api/chat──▶ backend/server.js (VPS)
                                  │
                                  ▼
                          PRIVACY GATEWAY   ── детекторы, entity linking,
                                  │            классификатор жалоб, редактура
                                  ▼
                       SanitizedPlannerRequest ──▶ провайдер LLM (планировщик)
                                  │                        │
                                  │                  строгий JSON
                                  ▼                        ▼
                          локальный план ◀── отказ ── SCHEMA VALIDATOR
                                  │                        │
                                  └────────┬───────────────┘
                                           ▼
                                    POLICY ENGINE ──▶ EXECUTOR ──▶ справочник
                                                                        │
                                  Браузер ◀── RESULT BUILDER ◀──────────┘
```

**Главный инвариант:** внешняя модель никогда не является доверенным
компонентом. У неё нет учётных данных к хранилищам, она не видит ни ФИО,
ни идентификаторов, ни координат, ни описания жалоб, и её ответ считается
недоверенным вводом независимо от того, что написано в системном промпте.

Отправить сырой ввод наружу нельзя не по соглашению, а по конструкции:
`planner/client.js` принимает только `SanitizedPlannerRequest`, создать
который умеет единственный модуль `privacy/gateway.js`. Это закреплено
правилом ESLint и тестом `tests/boundary.test.js`.

По умолчанию (`PRIVACY_OUTBOUND_MODE=structured`) в запросе нет ни одного
слова пользователя — только описание из перечислимых значений и меток.
Проверка на размеченном наборе (`npm run eval:privacy`,
[`docs/privacy-evaluation.md`](docs/privacy-evaluation.md)): 0 утечек на
14 728 примерах с персональными данными; её десятая часть входит в
`npm test`. `npm run test:security` прогоняет все тесты в обоих режимах.

Что делает функция `backend/api/chat.js`:

- принимает только `POST`, проверяет `Origin` на совпадение с собственным хостом
  (или со списком `ALLOWED_ORIGINS`);
- режет тело запроса на 32 КБ, историю — до 12 сообщений по 1000 символов;
- ставит таймаут 20 секунд на обращение к провайдеру, не следует за его
  редиректами и читает не больше 256 КБ ответа;
- ограничивает частоту: 20 запросов за 5 минут с адреса, бюджет процессорного
  времени на адрес, очередь разбора и общий предохранитель нагрузки;
  обращения к модели — 300 за 5 минут и `AI_DAILY_CALL_LIMIT` в сутки;
- передаёт запрос конвейеру `backend/pipeline.js`; прямого обращения
  к модели в этом файле больше нет;
- прогоняет итоговое действие через `shared/contract.js` — белые списки
  и лимиты длины для каждого поля;
- никогда не пересылает клиенту текст ошибки провайдера и **не пишет его
  в логи**: провайдеры регулярно возвращают в теле ошибки фрагмент
  присланного запроса.

Логирование идёт через `observability/safeLogger.js`: белый список полей,
чёрный список поверх него, отбрасывание объектов произвольной формы и
проверка каждого строкового значения детекторами. Ошибки логируются только
кодом — без `message` и без стека. Соответствия токенов не логируются никогда.

Запуск проверок:

```bash
npm test          # все тесты, включая приёмочные сценарии и аудиты
npm run lint      # в том числе правило границы доверия
```

Системный промпт лежит в `backend/planner/prompts.js` — только на сервере.
Его нельзя ни прочитать из бандла, ни подменить запросом с клиента.

Регулярные выражения детекторов работают на сыром тексте пользователя.
Каждое новое выражение проверяйте на катастрофический перебор: начало
совпадения отсекайте просмотром назад (`(?<!\p{L})`), длины ограничивайте,
соседние квантификаторы не должны совпадать по одним и тем же символам.
Тест `tests/third-audit.test.js` держит время разбора враждебного ввода.

## 3. Инъекции в промпт

Вывод модели управляет состоянием интерфейса (фильтры, поиск, маршрут),
поэтому он считается недоверенным независимо от того, что написано в промпте.

- `sanitizeAiAction()` приводит каждое поле к белому списку или к `null`;
  режимы транспорта, сортировки, форма собственности и тип карточки
  сверяются с перечислениями;
- названия районов, клиник, типов учреждений и услуг применяются только если
  реально присутствуют в справочниках приложения;
- из строк вырезаются управляющие символы, невидимые разделители и
  bidi-оверрайды (`‪`–`‮`), которыми маскируют вставки;
- та же нормализация повторяется на клиенте — состояние UI не должно зависеть
  от того, что пришло по сети.

XSS в этой части не возникает: весь текст модели рендерится React как
текстовый узел, `dangerouslySetInnerHTML` в проекте не используется.
Единственное место с `innerHTML` — `L.divIcon` в маркерах карты; значения там
приводятся функциями `sanitizeColor` / `sanitizeLabel`.

## 4. Заголовки

Выставляются в `backend/http/securityHeaders.js` на каждом ответе сервера;
если статику отдаёт nginx — сниппетом из `docs/deployment.md`:

- `Content-Security-Policy` — `default-src 'self'`, единственный внешний
  хост — тайлы `*.tile.openstreetmap.org` в `img-src`; `connect-src 'self'`;
  `frame-ancestors 'none'`, `object-src 'none'`;
- `Strict-Transport-Security` — 2 года, `includeSubDomains`, `preload`;
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`;
- `Referrer-Policy: strict-origin-when-cross-origin`;
- `Permissions-Policy` — геолокация разрешена только собственному origin,
  камера, микрофон, платежи и датчики запрещены;
- `Cross-Origin-Opener-Policy` / `Cross-Origin-Resource-Policy: same-origin`.

`style-src` содержит `'unsafe-inline'`: этого требуют инлайновые стили Leaflet
и React. Убрать можно только вместе с переходом на nonce-стили.

## 5. Данные пользователя

- Координаты запрашиваются через `navigator.geolocation` и никуда не
  отправляются: расстояния считаются в браузере.
- Маршруты строит собственный движок (`backend/routing`, см.
  `docs/routing.md`): координаты не покидают доверенный контур. Прежнее
  обращение к публичному OSRM убрано, вместе с ним из `connect-src`
  исчез последний сторонний хост.
- Остались тайлы OpenStreetMap: по запросу тайла видно лишь то, какой
  участок карты открыт. Упомяните их в политике конфиденциальности,
  а также укажите авторство данных OSM (лицензия ODbL).
- В `localStorage` хранятся избранное, тема, id выбранной программы ДМС
  (без номера полиса) и флаг демо-режима. Значения валидируются при чтении:
  повреждённые данные заменяются значением по умолчанию.
- Текст поиска отражается в адресе страницы (`?q=`), чтобы ссылкой можно
  было поделиться. Поэтому журнал nginx пишется без строки запроса
  (`log_format` в `docs/deployment.md`).
- Персональных данных пациентов приложение не собирает и не хранит.
- Текст запроса к ИИ проходит Privacy Gateway до любого обращения к внешней
  модели: ФИО, телефоны, email, СНИЛС, ОМС, паспортные данные, координаты,
  адреса и идентификаторы заменяются session-токенами с TTL, а сырое описание
  жалоб не покидает доверенный контур вовсе — наружу уходит только
  производный список профилей специалистов.
- Токены действительны в пределах одной сессии: ключ выводится как HMAC
  от идентификатора сессии, поэтому токен одной вкладки физически не
  разыменовывается в другой.
- Это **псевдонимизация, а не обезличивание**: соответствие обратимо при
  доступе к хранилищу. Утверждать на этом основании соответствие 152-ФЗ
  нельзя — перечень вопросов к юристу в разделе 10 архитектурного документа.

## 6. Сборщик данных

Сборщик (`tools/data`) читает чужие сайты, поэтому всё, что он приносит,
считается недоверенным:

- ходит только на http(s) из `data/sources.json`, не на локальные и
  внутренние адреса; редиректы — вручную и только в пределах того же сайта;
- читает не больше 3 МБ тела по мере поступления (защита от «gzip-бомб»),
  robots.txt — не больше 256 КБ; кодировка — из заголовка или `<meta>`;
- разбирает HTML линейным проходом, без регулярных выражений с перебором;
- режет управляющие символы и знаки направления текста — вывод `data:review`
  нельзя переписать ESC-последовательностями со страницы;
- телефон и сайт клиники, адрес, пропажа врача, рост цены больше 20 % от
  последней одобренной — только через человека; новый источник попадает в
  справочник после подтверждения в `npm run data:review`;
- сайт клиники принимается, только если он того же сайта, что и источник;
  координаты из описания источника главнее страницы;
- `shared/privateCatalog.js` проверяет ссылки (только http/https), телефоны,
  длины строк, координаты (в пределах республики) и стаж.

## 7. Что осталось сделать

1. **Отозвать скомпрометированные ключи.** Ключ из прежнего бандла и токен
   GitHub, отправленный в переписку, считайте публичными. Удалите
   `VITE_OPENROUTER_API_KEY` из `.env` и выпустите новый ключ модели.
2. **Вынести rate-limit во внешний стор** (Upstash Redis), если серверов
   станет больше одного: счётчики живут в памяти процесса.
3. **Проверить git-историю** на предмет ранее закоммиченных ключей:
   ```bash
   git log --all -p -S 'sk-' -- .env .env.example src/ | head -50
   ```
   Если ключ находится в истории — недостаточно удалить файл, нужен
   `git filter-repo` и принудительный пуш, плюс отзыв ключа.
4. **Регулярный `npm audit`.** `npm run audit:security` перед каждым релизом.
5. **Подключить капчу или подпись сессии** к `/api/chat`, если появится
   заметный поток автоматических запросов.
6. **Задать `PRIVACY_TOKEN_SECRET`** в окружении. Без него берётся случайный
   секрет процесса: соответствия токенов не переживают рестарт.
7. **Проверить инфраструктурное логирование.** Privacy Gateway не поможет,
   если reverse proxy пишет тела запросов, а Sentry или APM подключён
   с автоматическим захватом body. Это настраивается вне кода.
8. **Юридическая проверка.** Раздел 10 в
   [`docs/privacy-architecture.md`](docs/privacy-architecture.md) — список
   вопросов по 152-ФЗ, на которые код ответить не может.
9. **Исправить накопленные ошибки ESLint в `frontend/src/`** (3 штуки:
   `react-hooks/refs`, `react-refresh`). К privacy-слою отношения не имеют.
10. **Обновить Vite до 8.0.16+** (`npm install -D vite@^8.0.16`): в 8.0.0
    dev-сервер с `--host` отдавал файлы вне разрешённых каталогов.
11. **Свой поставщик тайлов карты** вместо `tile.openstreetmap.org`
    (правила OSM, см. `docs/deployment.md`).
12. **Политика обработки персональных данных** в интерфейсе — до того, как
    появится запись к врачу с именем и телефоном.
