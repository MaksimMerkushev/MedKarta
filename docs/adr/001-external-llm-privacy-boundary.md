# ADR 001. Граница приватности при работе с внешним LLM

- **Статус:** принято
- **Дата:** 2026-09-21
- **Контекст проекта:** «МедКарта Казань», ИИ-навигатор по врачам и клиникам
- **Связанные документы:** [`docs/privacy-architecture.md`](../privacy-architecture.md), `SECURITY.md`

## Контекст

До этого решения `backend/api/chat.js` работал как прокси: брал `messages` из браузера
и передавал их провайдеру модели без изменений. Поле ввода подписано
«Опишите симптомы...», то есть интерфейс прямо предлагал написать
«Меня зовут Иван, неделю болит живот». Такой текст уходил наружу целиком.

Существовавшая санитизация (`shared/contract.js`) обрабатывала **выход**
модели — белые списки значений для интерфейса. Вход не обрабатывался никак.
Направление защиты было противоположно задаче.

Дополнительно: тело ошибки апстрима логировалось первыми 500 символами, а
провайдеры регулярно возвращают в нём фрагмент присланного запроса.

Нам нужно сократить передачу персональных и медицинских данных внешней
модели до технического минимума и сделать результат пригодным для аудита.
Правовая квалификация выполняется отдельно и этим решением не покрывается.

## Рассмотренные варианты

### A. Оставить прокси, усилить системный промпт

Добавить в промпт запрет выдавать чужие данные и просьбу не запоминать ввод.

Отклонено: промпт — просьба к недоверенному компоненту. Он не мешает
передаче данных наружу (данные уже ушли вместе с промптом) и не выдерживает
инъекцию. Ни одно свойство безопасности на нём держаться не может.

### B. Клиентская редактура перед отправкой

Заменять PII в браузере до обращения к `/api/chat`.

Отклонено: клиент недоверен, обходится DevTools за минуту; справочник
пришлось бы держать в бандле целиком (он уже там частично, но это отдельная
проблема); обновление правил требовало бы релиза фронтенда.

### C. Отказаться от внешней модели, только правила

Полностью детерминированный разбор запроса.

Отклонено как единственное решение: проигрывает в понимании естественного
языка, особенно на сложных маршрутах. Но реализовано как **обязательный
запасной путь** — см. решение.

### D. Локальная LLM сейчас

Отклонено по срокам и стоимости инфраструктуры. Архитектура готовится
к такому переходу: см. раздел 11 архитектурного документа.

### E. Privacy Gateway + внешняя модель в роли планировщика — **принято**

## Решение

1. **Внешняя модель — только семантический планировщик.** Она не получает
   данных, не имеет инструментов и учётных данных, не выполняет запросов.
   Её выход — план из конечного множества значений.

2. **Privacy Gateway обязателен по типам, а не по соглашению.** Внешний
   планировщик принимает `SanitizedPlannerRequest`; создать его можно только
   в `privacy/gateway.js` (приватный `Symbol`). Сигнатуры
   `generate(prompt: string)` не существует. Дублируется правилом ESLint
   и тестом по исходникам.

3. **Entity linking вместо open-domain NER.** Справочник врачей и клиник
   известен заранее, поэтому вопрос «является ли „Петрову“ врачом» решается
   точным поиском по индексу с морфологией и допуском на опечатки —
   детерминированно, на CPU, без выгрузки текста куда-либо.

4. **Session-scoped токены вместо реальных идентификаторов.** Ключ выводится
   как HMAC от `sessionId`; смещение алфавита меток тоже завязано на сессию,
   поэтому один врач получает разные токены в разных сессиях. TTL 900 секунд.

5. **Fail-closed с локальным планировщиком.** Номер документа, неуверенная
   классификация жалобы, остаточное имя после редактуры или слишком высокая
   доля редактуры — внешний вызов не делается. Чтобы отказ не превращался
   в отказ в обслуживании, план строит детерминированный локальный
   планировщик, а пользователю задаётся уточняющий вопрос.

6. **Сырой медицинский текст не покидает контур.** Локальный классификатор
   переводит жалобу в набор профилей; наружу уходит «Пользователь ищет
   врача по профилю: gastroenterologist, therapist». Режим
   `POLICY.medicalTextMode = 'strict'` не имеет переключателя намеренно.

7. **Вывод модели — недоверенный ввод.** Схемная валидация с отказом на
   неизвестное поле, затем Policy Engine с авторизацией токенов и бюджетом
   сложности. Отклонение — жёсткое: план не «чинится» частичным исполнением.

8. **Текст для пользователя собирается шаблонами.** Модель влияет на
   формулировку только через перечислимый `reply_hint`. Это закрывает канал,
   через который инъекция могла показать пользователю произвольную фразу,
   и снимает необходимость во втором вызове модели — который пришлось бы
   кормить реальными ФИО найденных врачей.

9. **Логирование по белому списку.** Идеальный Gateway бессмыслен, если текст
   затем уходит в Sentry или в логи функции.

## Что мы сознательно не используем

- **Aho-Corasick.** Рассматривался для поиска названий клиник. При лимите
  сообщения в 1000 символов окно из ≤150 токенов даёт ≤750 обращений
  к хэш-индексу — дешевле построения и обхода автомата и заметно проще
  в аудите. Автомат имел бы смысл на потоковом тексте в мегабайты.
- **Снисходительный парсер JSON.** «Вытащим объект из середины текста» —
  это способ принять вперемешку с планом ещё и текст инъекции.
- **Молчаливое отбрасывание неизвестных полей.** Скрывает от нас факт
  попытки выйти за контракт; вместо него отказ с отдельным кодом.
- **Pydantic и отдельный Python-сервис.** Проект — Node ESM на Vercel;
  второй рантайм, деплой и CI не окупаются. Строгие схемы реализованы
  собственным валидатором с перечислениями.

## Последствия

**Положительные.** Персональные и медицинские данные не покидают контур
в техническом минимуме случаев. Безопасность проверяема: 80 автотестов,
включая фиксацию точного текста исходящего запроса. Замена внешней модели
на локальную — одна строка сборки конвейера. Прототип инъекции больше не
имеет пути к данным.

**Отрицательные.** Ответы стали менее «живыми»: шаблоны вместо свободного
текста. Часть запросов уходит в fail-closed и требует уточнения —
классификатор жалоб консервативен намеренно. Добавилось ~2500 строк
инфраструктуры и новая задержка на анализ (≈7 мс на сообщение в 1000
символов). Появился новый чувствительный актив — Token Vault.

**Нейтральные.** Контракт ответа для интерфейса сохранён: `frontend/src/App.jsx` не
переписывался. Внешних зависимостей не добавлено.

## Проверка решения

```bash
npm test          # 80 тестов, включая приёмочный сценарий
npm run lint      # правило границы доверия
```

Ключевые тесты: `tests/outbound-leakage.test.js` (что физически уходит
наружу), `tests/boundary.test.js` (инвариант по исходникам),
`tests/pipeline.integration.test.js` (приёмочный сценарий целиком).
