# Инструкции администратору: почта, регистрация, защита суперадминистратора

Пошагово — что делать при запуске, включении почты и регистрации, при
потере доступа и инцидентах. Все команды — в терминале сервера, из каталога
приложения; базу они открывают ту же, что и сервер (останавливать его не
нужно). Пароли и ключи в этом документе не приводятся — только порядок
действий.

## 1. После обновления до схемы 5 (или сразу до 6)

1. **До** `git pull`: копия базы — `npm run accounts -- backup --out /backup/accounts-$(date +%F).sqlite`.
2. Задайте ключ двухфакторной защиты в окружении сервиса
   (`MFA_SECRET_KEY`, `openssl rand -base64 32`) **или** убедитесь, что после
   первого запуска появился `var/accounts/secrets/mfa.key` (права 600), и
   скопируйте его в надёжное место отдельно от базы.
3. Задайте `PUBLIC_BASE_URL=https://navimed.tech` (адрес сайта для ссылок и
   ключей доступа).
4. Перезапустите сервис. При миграции сервер сам сохранит копию
   `medkarta.sqlite.before-v5-….bak`. Все сессии завершатся — войти нужно
   заново.
5. `npm run accounts -- status` — схема 6 (или 5 на прежней версии), регистрация «только по
   приглашению», список сотрудников без второго фактора.
6. Обновите сниппет заголовков nginx ([deployment.md](deployment.md)):
   `Permissions-Policy` с `publickey-credentials-get=(self)` и
   `publickey-credentials-create=(self)`, `Referrer-Policy: no-referrer` для
   `/activate`, `/register/confirm`, `/email/confirm`.

### Обновление 5 → 6 (исправления аудита)

1. Копия базы (`backup`), как выше. Ключ `MFA_SECRET_KEY` / `mfa.key` **не
   менять**: из него теперь выводится и ключ писем в очереди — письма,
   не ушедшие до перезапуска, отправятся после него. Сменённый ключ — такие
   письма помечаются неотправленными (`key_changed`), ссылку запросят заново.
2. Перезапуск: миграция добавляет два столбца, копия
   `medkarta.sqlite.before-v6-….bak` создаётся сама. Аккаунты, пароли,
   факторы и сессии сотрудников не меняются; сессии без второго фактора у
   аккаунтов с MFA (если такие были) завершаются при первом запросе.
3. Что изменится для сотрудников: перед первым ключом доступа или кодом,
   перед ссылкой для смены пароля, сменой email, сбросом второго фактора,
   снятием ограничений входа, созданием сотрудника, восстановлением и
   разблокировкой панель попросит пароль и второй фактор (раз в 10 минут) —
   вход этого больше не заменяет. Новые ключи доступа сотрудников — только с
   PIN или биометрией; старые продолжают работать (в профиле у них подсказка).
4. `npm run accounts -- status` — схема 6.

## 2. Суперадминистратор: двухфакторная защита

1. Войдите в `/admin` паролем. Панель покажет «Включите двухфакторную
   защиту».
2. Добавьте **ключ доступа** (Touch ID / Face ID / Windows Hello / Android
   или аппаратный ключ FIDO2) — он устойчив к фишингу. Затем — второй способ
   на другом устройстве (ещё один ключ или приложение-аутентификатор):
   потеря единственного устройства не должна оставлять без доступа.
3. **Сохраните резервные коды** (10 штук, показываются один раз): распечатка
   в сейфе или менеджер паролей, не в той же почте. Каждый код — один раз;
   «Новые коды» в профиле гасят старые.
4. В «Профиль» → «Безопасность аккаунта» проверьте: «Включена», список
   способов, число резервных кодов.
5. То же сделает каждый сотрудник при первом входе в панель — без этого
   панель не откроется.

## 3. Включение почты

1. Получите у провайдера SMTP-доступ и записи SPF/DKIM, настройте DMARC —
   [mail-setup.md](mail-setup.md).
2. Добавьте в окружение сервиса `SMTP_URL` (или `SMTP_HOST`…),
   `SMTP_FROM`, `PUBLIC_BASE_URL`; перезапустите.
3. `npm run accounts -- status` → «Почта: SMTP …».
4. Проверка **только на своих адресах**: приглашение на свой второй ящик,
   «Нет пароля или забыли его?» на нём же.

## 4. Открытие регистрации

1. Почта работает (раздел 3), письма не попадают в «Спам».
2. Опубликованы политика обработки ПДн и текст согласия; решены вопросы
   152-ФЗ (уведомление Роскомнадзора, размещение базы). Это решение
   владельца с юристом — код соответствия не обеспечивает.
3. `REGISTRATION_MODE=open` в окружении, перезапуск. На `/login` появится
   «Создать аккаунт», `/register` начнёт принимать заявки.
4. Закрыть — `REGISTRATION_MODE=invite_only` и перезапуск; созданные
   аккаунты остаются.

## 5. Потеря доступа

| Ситуация | Что делать |
|---|---|
| пользователь забыл пароль | «Нет пароля или забыли его?» на `/login` (при настроенной почте) или `npm run accounts -- access-link --email …` и передать ссылку лично. Если включена MFA, по ссылке пароль сменится только со вторым фактором владельца |
| пользователь потерял телефон, есть резервный код | войти паролем и резервным кодом, в профиле удалить старый способ и добавить новый |
| «Пользователь» потерял **все** факторы (и коды) | установить личность (см. ниже), затем карточка → «Управление» → «Сбросить двухфакторную защиту»: ввести email и как подтверждена личность (в журнал), подтвердить свою личность паролем и ключом. Удаляются факторы и коды, завершаются сессии, владельцу — письмо. Забыт и пароль — после сброса обычная ссылка |
| сотрудник потерял **все** факторы (и коды) | установить личность владельца вне системы (лично или по заранее известному каналу), затем на сервере `npm run accounts -- mfa-reset --email …` — команда попросит ввести email ещё раз; удаляются факторы, коды, все сессии и доверенные устройства; после входа — сразу настроить MFA. Из админ-панели второй фактор сотрудника не сбрасывается |
| суперадминистратор потерял и пароль, и факторы | на сервере: `mfa-reset --email …`, затем `access-link --email …` (ссылка выводится в терминал), задать новый пароль, настроить MFA |
| аккаунт суперадминистратора понижен или заблокирован (ошибка, старая база) | `npm run accounts -- restore-admin --email …` |
| вход с незнакомых устройств приостановлен из-за подбора | убедиться, что попытки делал сам владелец; кнопка «Снять ограничения входа» в карточке или `npm run accounts -- unlock --email …` |

Сброс факторов **не делается по письму**, а у сотрудников — и из
админ-панели: иначе захват почты или чужой сессии сотрудника давал бы
захват аккаунта.

**Как подтвердить личность перед сбросом второго фактора пользователя.**
Не по письму с того же адреса и не по звонку с неизвестного номера:
злоумышленник может управлять ящиком. Подходит: лично с документом или
видеозвонок со сверкой документа и данных, известных МедКарте (имя, дата
регистрации, недавние действия).
В поле «Как подтверждена личность» — способ и дата, без номеров документов.
Если есть сомнения — не сбрасывайте: письмо «Двухфакторная защита сброшена»
владелец получит в любом случае, но вход злоумышленник получит раньше.

## 6. Подозрение на взлом

1. Карточка пользователя → «Завершить все сессии» (или сам пользователь —
   «Выйти везде» в профиле).
2. Выдать ссылку для смены пароля (`reset-password --email …` — она же
   завершает сессии).
3. Если затронут второй фактор — сброс (пользователь — из карточки,
   сотрудник — `mfa-reset` на сервере), затем новая настройка. Ссылка для
   смены пароля у аккаунта с MFA без второго фактора не сработает.
4. Журнал действий (`/admin/audit`) и вкладка «Безопасность» в карточке:
   входы, неудачи, смены email и факторов.
5. Сотрудник с подозрением на компрометацию — блокировка (`/admin`,
   «Заблокировать»): сессии и ссылки гаснут сразу.

## 7. Резервные копии и восстановление

- Ежедневно: `npm run accounts -- backup --out /backup/accounts-$(date +%F).sqlite`,
  хранить ограниченный срок (например, 30 дней), права 600.
- Ключ `MFA_SECRET_KEY` (или файл `mfa.key`) — отдельно от копий базы:
  копия без ключа не даёт проверить коды, ключ без копии бесполезен.
- Восстановление: остановить сервис → положить копию на место
  `var/accounts/medkarta.sqlite` (права 600) и тот же ключ → запустить →
  `npm run accounts -- status`. Если ключ утрачен — коды приложений и
  резервные коды не проверятся: `mfa-reset` для каждого сотрудника, ключи
  доступа продолжат работать (их проверка ключа не требует).

## 8. Регулярно

- Раз в месяц: `npm run accounts -- list-staff` — нет ли лишних сотрудников;
  `status` — нет ли сотрудников без второго фактора.
- После увольнения сотрудника — роль «Пользователь» или блокировка.
- Отчёты DMARC — раз в неделю первые месяц-два.
