# Аккаунты, роли и админ-панель

Аккаунт хранит то, ради чего пользователь возвращается, — **программу ДМС**,
**избранных врачей** и демо-записи — и даёт доступ к ИИ-ассистенту. Сотрудникам
аккаунт открывает **админ-панель** (`/admin`): пользователи, блокировки, роли,
сессии, журнал действий, мониторинг и настройки.

**Публичной регистрации нет.** Аккаунты создаёт администратор в админ-панели
(или команда CLI); пользователь получает временный пароль и меняет его при
первом входе. Маршрута `POST /api/auth/register` больше нет — ответ 404.

| Где | Кому | Что там |
|---|---|---|
| карта, кнопка аккаунта | всем | вход, ДМС, избранное, демо-аккаунты; плашка «Аватар · Имя · Профиль · Выйти» |
| `/profile` | вошедшим | фото, имя и фамилия, смена пароля, свои сессии и история входов |
| `/admin` | ролям с `admin.access` | разделы ниже, каждый — по своему разрешению |

## Роли и разрешения

| Роль | Ранг | По умолчанию может |
|---|---|---|
| `user` — Пользователь | 0 | только сервис и свой профиль |
| `moderator` — Модератор | 1 | вход в панель, просмотр пользователей, блокировка |
| `admin` — Администратор | 2 | всё, кроме безвозвратного удаления, изменения матрицы ролей и настроек |
| `superadmin` — Суперадминистратор | 3 | всё |

Разрешения ([rbac.js](../backend/accounts/rbac.js)): `admin.access`,
`dashboard.view`, `users.view`, `users.create`, `users.edit`, `users.block`,
`users.password`, `users.sessions`, `users.archive`, `users.delete`,
`users.export`, `roles.assign`, `roles.manage`, `audit.view`, `system.view`,
`settings.view`, `settings.edit`. Набор для `admin` и `moderator`
суперадминистратор меняет в разделе «Роли и права» (таблица
`role_overrides`); `roles.manage` и `settings.edit` есть только у
суперадминистратора, а зависимости (например, `users.delete` требует
`users.archive`) проверяет сервер.

Правила, которые проверяет **сервер** (интерфейс только прячет кнопки):

- менять можно только аккаунты **ниже своей роли**, суперадминистратор — любые,
  кроме своего; над собой — ни блокировки, ни смены роли, ни удаления;
- назначать можно только роли ниже своей (суперадминистратор — любую);
- **последний активный суперадминистратор** не может быть понижен,
  заблокирован, отправлен в архив или удалён — проверка и изменение идут в
  одной транзакции, отказ пишется в журнал;
- каждый запрос принимает только перечисленные поля: `role`, `status`,
  `passwordHash` и т. п. в теле `PATCH` игнорируются (защита от mass assignment);
- правка карточки и роли — с номером версии (`version`): если карточку
  успели изменить в другой вкладке, ответ `409 conflict`.

База — один файл `var/accounts/medkarta.sqlite` (права 600, каталог 700,
`ACCOUNTS_DB_PATH` переопределяет). SQLite выбран под сервер в 1 ядро и 2 ГБ:
отдельный процесс СУБД не нужен. Требуется **Node 22.13+** (`node:sqlite` без
флага); на более старом Node аккаунты выключаются, карта работает.

## Что хранится (схема 3)

| Таблица | Что | Зачем |
|---|---|---|
| `users` | email, имя и фамилия, хэш пароля (scrypt), роль, статус, срок и причина блокировки, «сменить пароль», время входа, последней активности и смены пароля, счётчик неудачных входов, кто создал, версия, программа ДМС; у демо-копий — шаблон и SHA-256 от токена браузера | аккаунт |
| `sessions` | SHA-256 от токена, публичный id для отзыва, срок, последняя активность, «Chrome 129 · macOS», сеть /24 (IPv6 — /48) | вход |
| `favorites` | id врача или учреждения | избранное |
| `auth_events` | вход, неудача, отказ (заблокирован), выход, смена пароля, отзыв сессий; клиент и сеть | история входов, график входов |
| `audit_log` | кто, что, над кем, результат (`ok`/`denied`/`failed`), детали без секретов | журнал действий |
| `user_blocks` | блокировки, разблокировки и окончания срока с причиной и автором | история блокировок |
| `user_activity` | пара «пользователь, московский день» | DAU/WAU/MAU без хранения запросов |
| `avatars` | очищенное изображение (≤ 256 КБ) и его хэш | фото профиля |
| `settings`, `role_overrides` | значения из раздела «Настройки» и изменённые наборы разрешений | настройка без правки кода |

**Не хранится:** пароли в открытом виде, полный IP, запросы к ассистенту,
симптомы, местоположение, история поиска, номер полиса, медицинские данные.
В журнале действий email показывается маской (`m***@bk.ru`); пароли, хэши и
токены туда не попадают.

Миграции — по `PRAGMA user_version` при открытии базы, в транзакции: схема 1 →
2 (демо-копии) → 3 (роли, статусы, журналы). Прежние аккаунты получают роль
`user`, статус `active`, имя переходит в `first_name`. Отката нет — перед
обновлением сделайте копию (раздел «Резервные копии»).

## Сессии

- Токен — 32 случайных байта в cookie `mk_session`: `HttpOnly`,
  `SameSite=Lax`, `Path=/api`; `Secure` — всегда при `NODE_ENV=production`,
  иначе — если запрос пришёл по HTTPS (за nginx — по `X-Forwarded-Proto` от
  доверенного прокси). В базе только SHA-256: утечка базы не даёт войти.
- Срок — скользящий: сессия без активности живёт `sessions.idleDays` (14 дней),
  но не дольше `sessions.maxDays` (30 дней) от входа. Активность отмечается не
  чаще раза в минуту. Демо-сессия — 12 часов.
- Не больше `sessions.maxPerUser` (10) сессий на аккаунт, старшая вытесняется.
- Смена пароля завершает все остальные сессии; блокировка, архив, сброс пароля
  администратором и удаление — все сессии пользователя сразу.
- «Активность только что» — время последнего запроса с этой сессией, а не
  «онлайн»: признака присутствия (heartbeat) нет.

## Безопасность

- **Пароли** — scrypt (N=2¹⁵, r=8, p=3 — параметры уровня рекомендаций OWASP для
  scrypt; Argon2id в Node 22 без сторонних модулей недоступен), соль на каждый
  пароль, сравнение за постоянное время; хэши со старыми параметрами
  пересчитываются при следующем входе. Пароль — не короче 8 символов, не из
  частых утечек, не одни цифры, не один повторяющийся символ и не содержит
  email. Временный пароль — 20 символов без похожих букв (`Abcd-…`),
  показывается один раз.
- **Вход** — для несуществующего email проверка идёт по «пустышке», по
  времени ответа нельзя узнать, есть ли аккаунт. Статус (заблокирован, в
  архиве) сообщается **только после верного пароля** — иначе это была бы
  проверка существования аккаунта.
- **Перебор** — 20 попыток входа за 15 минут с адреса и
  `auth.maxFailedPerEmail` (10) неудачных входов за 15 минут на один email со
  всех адресов: дальше даже верный пароль ждёт паузы (429). Неудачи считаются
  и в аккаунте (`failed_logins`), видны в карточке и на дашборде.
- **Нагрузка** — не больше двух расчётов scrypt одновременно и 32 в очереди;
  сверх этого — 503 «попробуйте через минуту».
- **CSRF** — изменяющие запросы (и `DELETE`) принимаются только как
  `application/json` со своего Origin и с `Sec-Fetch-Site: same-origin`.
- **Лимиты** — `/api/me` 300 запросов за 5 минут с адреса (смена пароля —
  10 за 15 минут), `/api/admin` — 600 за 5 минут.
- **Аватар** — PNG, JPEG или WebP до 256 КБ и 1024 px по стороне (браузер
  заранее уменьшает фото до 256 px); тип определяется по сигнатуре, а не по
  расширению; метаданные (EXIF с геометкой, комментарии,
  XMP) вырезаются; анимация отклоняется; отдаётся с `Content-Security-Policy:
  sandbox`, `nosniff` и `Cross-Origin-Resource-Policy: same-origin`.
- **Экспорт CSV** — только разрешению `users.export`, пишется в журнал;
  ячейки, начинающиеся с `=`, `+`, `-`, `@`, экранируются (формулы не
  выполнятся в Excel). Внешние сервисы и LLM таблицы пользователей не видят.
- **Настройки** — только перечисленные ключи с проверкой значений. Переменных
  окружения, ключей API, секретов, перезапуска сервера и выполнения команд
  через веб-интерфейс нет.
- **Удаление** — `PRAGMA secure_delete`: удалённые записи затираются в файле
  базы. Безвозвратное удаление требует ввести email пользователя.
- **Журналы сервера** — только факт события (`account.login: ok/failed`), без
  email, имени и пароля: их отсекает белый список полей `safeLogger`.

| Карточка | `users.view` и др. | вкладки «Профиль», «Управление» (имя и email, роль, блокировка, архив, сессии, временный пароль, удаление), «Безопасность» (сессии, история входов, блокировки), «Аудит» |

| Сессии | `users.sessions` | все активные сессии с отзывом |
| Журнал действий | `audit.view` | поиск, фильтры по действию, результату и датам, раскрываемые детали |
| Система | `system.view` | компоненты (база, демо-запись, граф дорог, планировщик, хранилище меток, аналитика), версия, коммит, Node, память, счётчики запросов |
| Настройки | `settings.view`; правка — `settings.edit` | название, контакты поддержки, сообщение о работах, ассистент вкл/выкл и «только после входа», демо-кнопки, сроки сессий, порог неудачных входов, сроки хранения журналов |

Числа «сейчас» на дашборде точные (запрос к базе), счётчики ошибок — с момента
запуска процесса. DAU — уникальные пользователи (без демо-копий), сделавшие
хотя бы один запрос с действующей сессией за московские сутки.

## Первый запуск

### Главный суперадминистратор

Аккаунт `maximka2703@bk.ru` («Максим», роль `superadmin`) создаётся **один
раз**; пароль не хранится ни в коде, ни в документации.

Вариант 1 — при запуске сервера:

```bash
ADMIN_BOOTSTRAP_PASSWORD='…придумайте сами…' npm start
```

Если такого email ещё нет, сервер создаст аккаунт и запишет в журнал только
`account.bootstrap: created`. Повторный запуск ничего не меняет — ни пароль,
ни роль. После первого входа уберите переменную из окружения.
`ADMIN_BOOTSTRAP_EMAIL` меняет адрес.

Вариант 2 — командой, пароль вводится в терминале и не отображается:

```bash
npm run accounts -- bootstrap
```

### Три тестовых пользователя

Только для локального запуска и staging:

```bash
npm run accounts -- seed-test-users
```

Создаются `anna.smirnova@medkarta.test`, `timur.khairullin@medkarta.test`,
`elena.kovaleva@medkarta.test` с ролью «Пользователь». Случайные пароли
печатаются **один раз** в терминал (в файл или журнал — только с
`--print-secrets`); при первом входе пароль нужно сменить. Существующие
аккаунты пропускаются. При `NODE_ENV=production` или `APP_ENV=production`
команда отказывается без `--allow-production`.

### Потеря доступа

```bash
npm run accounts -- reset-password --email адрес   # временный пароль, все сессии завершены
npm run accounts -- restore-admin --email адрес    # вернуть роль superadmin и статус «активен»
npm run accounts -- list-staff                     # кто с какими ролями
npm run accounts -- status                         # схема, число аккаунтов, суперадминистраторы
```

Команды работают с той же базой, что и сервер (останавливать его не нужно),
и пишутся в журнал действий как «Система (CLI)».

## Демо-аккаунты

При `DEMO_DATA=on` и включённой настройке «Кнопки демо-аккаунтов» кнопки
«Войти как …» открывают четыре вымышленных профиля с демо-программами ДМС и
избранным (`@medkarta.example`). Пароля у них нет — только кнопка. В
админ-панели демо-копии видны с фильтром «Демо-копии», но не управляются и в
статистику не входят.

Каждый браузер получает **свою копию** профиля — общего демо-кабинета нет:

- при первом демо-входе сервер ставит cookie `mk_demo` — 32 случайных байта,
  `HttpOnly; SameSite=Lax; Path=/api`, срок 30 дней; в базе только SHA-256
  от неё (`users.demo_owner`);
- пара «профиль + браузер» — один аккаунт. После выхода и нового входа в том
  же браузере программа ДМС, избранное и демо-записи на месте; другой браузер
  под тем же профилем начинает с исходного состояния и чужих изменений не
  видит; разные профили в одном браузере — разные аккаунты;
- испорченная cookie заменяется новой; чтобы попасть в копию другого
  браузера, нужен его токен;
- копия, в которую не входили 30 дней, удаляется вместе с сессиями и
  избранным; копий не больше 10 000 — при переполнении удаляются самые давние.

Остальные правила демо-профилей:

- имя поменять нельзя (это вымышленный профиль), удалить копию вручную тоже
  нельзя — она удаляется сама;
- демо-сессия живёт 12 часов, входов на копию — до 10, демо-входов с адреса —
  200 за 15 минут;
- избранное и ДМС, набранные гостем, в демо-аккаунт **не переносятся** —
  они откладываются в браузере и возвращаются после выхода. В настоящий
  аккаунт избранное гостя, наоборот, добавляется при входе.

## Записи и переписка

- **Демо-записи.** Запись, сделанная после входа, привязывается к id аккаунта
  и видна в «Мои демо-записи» только ему (`GET /api/demo/bookings/mine`, до
  50 последних): у настоящего аккаунта — на любом устройстве, у демо-копии —
  в её браузере. Записи гостя хранятся в браузере
  (`medkarta.demo-bookings`): пока выполнен вход, они не показываются и в
  кабинет не переносятся, после выхода видны снова. Удаление аккаунта
  отвязывает его записи: слоты остаются занятыми, но записи больше ничьи.
- **Ассистент — только после входа.** Гость по кнопке ассистента видит
  предупреждение с кнопкой «Войти в кабинет», а сервер отвечает на его запрос
  к `/api/chat` кодом `401 login_required`
  ([chatAccess.js](../backend/api/chatAccess.js)); с временным паролем —
  `403 password_change_required`. Если база аккаунтов недоступна — `503
  accounts_unavailable`. Настройка «ИИ-ассистент включён» выключает его для
  всех (`503 assistant_disabled`), «Ассистент только после входа» (по
  умолчанию — из `CHAT_REQUIRES_ACCOUNT`) открывает его гостям. В конвейер
  `/api/chat` и к модели из аккаунта не уходит ничего — проверяется лишь факт
  входа.
- **Переписка с ассистентом** живёт только в открытой вкладке и на сервере не
  хранится. При входе и выходе интерфейс очищает её вместе с подборками под
  ней и открытым окном записи и сбрасывает идентификатор диалога
  (`medkarta.ai.session`), к которому сервер привязывает плейсхолдеры.

## Персональные данные

Email, имя, фамилия, фото, история входов (время, браузер, сеть /24) — это
персональные данные. Медицинских данных в аккаунте нет: программа ДМС — id из
справочника, избранное — id врачей. Соответствие 152-ФЗ отдельно **не
проверялось**; прежде чем выдавать аккаунты посторонним людям, нужно как
минимум:

1. опубликовать политику обработки персональных данных;
2. подать уведомление об обработке ПДн в Роскомнадзор;
3. убедиться, что сервер с базой находится в России (локализация);
4. согласовать сроки хранения журналов (настройки «История входов» и
   «Журнал действий»).

Это вопросы к юристу, а не к коду; см. также `docs/privacy-architecture.md`, раздел 10.

## Резервные копии

Горячая копия без остановки сервиса (`VACUUM INTO` — целостный снимок):

```bash
npm run accounts -- backup --out /backup/accounts-$(date +%F).sqlite
```

Делайте копию раз в сутки и **перед каждым обновлением** (миграции схемы
необратимы) — до `git pull`: команда открывает базу кодом, который сейчас
в каталоге, и новый код сначала применит миграцию. Если код уже обновлён,
копируйте файл базы при остановленном сервисе (`cp`) или
`sqlite3 … ".backup …"`. Восстановление — остановить сервис, положить копию на место
`var/accounts/medkarta.sqlite` (права 600), запустить. Удалённый аккаунт
остаётся в копиях, сделанных до удаления: храните копии ограниченный срок
(например, 30 дней с ротацией).

## Переход на PostgreSQL

`service.js` и `adminService.js` не знают про SQL — они вызывают методы
хранилища (`createUser`, `listUsers`, `createSession`, `addAudit`, …, полный
список — объект, который возвращает `createSqliteAccountStore`). Для
PostgreSQL достаточно написать `pgStore.js` с теми же методами и подставить
его в `createAccountContext`. Методы SQLite синхронные; при переходе их нужно
сделать асинхронными и добавить `await` в сервисах — это механическая правка,
а `transaction()` — заменить на `BEGIN … COMMIT` с одним соединением.
