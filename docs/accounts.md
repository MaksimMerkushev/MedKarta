# Личный кабинет

Кабинет хранит две вещи, ради которых пользователь возвращается: **программу
ДМС** и **избранных врачей**. Без входа всё это по-прежнему живёт в браузере;
после входа — в аккаунте и доступно с любого устройства.

## Что хранится

| Таблица | Поля | Зачем |
|---|---|---|
| `users` | email, имя, хэш пароля (scrypt), id программы ДМС | вход и программа ДМС |
| `sessions` | SHA-256 от токена, срок действия | вход без пароля 30 дней |
| `favorites` | id врача или учреждения из справочника | избранное |

**Не хранится:** запросы к ассистенту, симптомы, местоположение, история
поиска, номер полиса. В `/api/chat` не уходит ничего из кабинета.

## Устройство

```
frontend/src/AccountPanel.jsx   окно кабинета: вход, демо-аккаунты, ДМС, избранное
frontend/src/hooks/useAccount.js состояние кабинета в интерфейсе
frontend/src/services/account.js запросы к API
backend/api/account.js          HTTP: маршруты, cookie, защита от CSRF, лимиты
backend/accounts/service.js     логика: регистрация, вход, сессии, ДМС, избранное
backend/accounts/passwords.js   scrypt без внешних зависимостей
backend/accounts/sqliteStore.js хранилище на SQLite (node:sqlite)
```

База — один файл `var/accounts/medkarta.sqlite` (права 600, каталог 700).
SQLite выбран под сервер в 1 ядро и 2 ГБ: отдельный процесс СУБД не нужен,
а нагрузка кабинета — единицы запросов в секунду. Требуется **Node 22.13+**
(`node:sqlite` без флага). На более старом Node кабинет выключается сам,
остальной сайт работает как раньше.

### Переход на PostgreSQL

`service.js` не знает про SQL: он вызывает методы хранилища —
`createUser`, `getUserById`, `getUserByEmail`, `getUserByDemoKey`,
`updateDisplayName`, `updateDmsPlan`, `deleteUser`, `createSession`,
`getSession`, `deleteSession`, `purgeExpiredSessions`, `listFavorites`,
`countFavorites`, `addFavorites`, `removeFavorite`, `replaceFavorites`.
Для PostgreSQL достаточно написать `pgStore.js` с теми же методами (схема —
те же три таблицы) и подставить его в `getDefaultAccountService`. Методы
SQLite синхронные; при переходе их нужно сделать асинхронными и добавить
`await` в сервисе — это механическая правка.

## API

| Метод и путь | Что делает |
|---|---|
| `GET /api/account` | кто вошёл, программа ДМС, избранное, доступные функции |
| `PATCH /api/account` | `{displayName}` или `{dmsPlanId}` (только из справочника) |
| `DELETE /api/account` | `{confirm: true}` — удалить аккаунт, сессии и избранное |
| `POST /api/account/favorites` | `{action: add \| remove \| merge, ids: [...]}` |
| `POST /api/auth/login` | `{email, password}` |
| `POST /api/auth/register` | `{email, password, displayName, consent: true}` |
| `POST /api/auth/demo` | `{account: anna \| family \| kids \| basic}` |
| `POST /api/auth/logout` | выход |

## Безопасность

- **Пароли** — scrypt (N=16384, r=8, p=1), соль на каждый пароль, сравнение
  за постоянное время. Для несуществующего email проверка идёт по
  «пустышке» — по времени ответа нельзя узнать, есть ли аккаунт.
  Самые распространённые пароли из утечек и пароли из одного символа
  отклоняются при регистрации.
- **Нагрузка** — не больше двух расчётов scrypt одновременно и 32 в очереди;
  сверх этого — ответ 503 «попробуйте через минуту», а не «неверный пароль».
  Поток входов не занимает потоки, которыми сервер отдаёт файлы.
- **Сессия** — 32 случайных байта в cookie `mk_session`: `HttpOnly`,
  `SameSite=Lax`, `Path=/api`. Флаг `Secure` — всегда при
  `NODE_ENV=production`, иначе — если запрос пришёл по HTTPS (за nginx —
  по `X-Forwarded-Proto` и только от доверенного прокси). В базе только
  SHA-256 от токена: утечка базы не даёт войти. Не больше 10 входов на
  аккаунт, старший вытесняется.
- **CSRF** — изменяющие запросы принимаются только как `application/json`
  со своего Origin и с `Sec-Fetch-Site: same-origin`.
- **Перебор** — 20 попыток входа и регистрации за 15 минут с адреса и
  10 неудачных входов за 15 минут на один email (со всех адресов вместе):
  после этого даже верный пароль ждёт паузы — ответ 429.
- **Удаление** — `PRAGMA secure_delete`: удалённые аккаунты затираются в
  страницах файла базы, а не только помечаются свободными.
- **Окончание сессии** — если сервер ответил 401 (сессия истекла, вытеснена
  или аккаунт удалён с другого устройства), интерфейс сразу выходит из
  кабинета и убирает избранное и ДМС аккаунта с устройства. То же — при
  открытии сайта, если сессия кончилась, пока он был закрыт.
- **Журналы** — только факт события (`account.login: ok/failed`), без email
  и имени: их отсекает белый список полей `safeLogger`.

## Демо-аккаунты

При `DEMO_DATA=on` создаются четыре вымышленных пользователя с демо-программами
ДМС и избранным (`@medkarta.example`). Пароля у них нет — только кнопка
«Войти как …», и только при включённом демо. Каждый вход возвращает
демо-аккаунт к исходному состоянию: следующий зритель не видит, что поменял
предыдущий.

Демо-аккаунт общий, поэтому:

- имя в нём поменять нельзя (иначе через него можно показывать текст
  следующим зрителям), удалить его тоже нельзя;
- демо-сессия живёт 12 часов, сессий на один демо-аккаунт — до 2000, а
  демо-входов с адреса — 200 за 15 минут: зрители не выбивают друг друга;
- избранное и ДМС, набранные гостем, в демо-аккаунт **не переносятся** —
  они откладываются в браузере и возвращаются после выхода. В настоящий
  аккаунт избранное гостя, наоборот, добавляется при входе.

## Регистрация и 152-ФЗ

Регистрация реализована, но **выключена по умолчанию**
(`ACCOUNTS_REGISTRATION=on` включает). Email и имя — персональные данные.
Прежде чем открывать регистрацию для всех, нужно:

1. опубликовать политику обработки персональных данных и сослаться на неё
   рядом с галочкой согласия;
2. подать уведомление об обработке ПДн в Роскомнадзор;
3. убедиться, что сервер с базой находится в России (локализация);
4. решить, нужно ли подтверждение email (сейчас его нет).

Это вопросы к юристу, а не к коду; см. также `docs/privacy-architecture.md`, раздел 10.

## Резервные копии

Копируйте файл базы раз в сутки вместе с `.env`. Горячая копия без остановки
сервиса: `sqlite3 var/accounts/medkarta.sqlite ".backup '/backup/accounts-$(date +%F).sqlite'"`.

Удалённый аккаунт остаётся в копиях, сделанных до удаления. Храните копии
ограниченный срок (например, 30 дней с ротацией) и укажите этот срок в
политике обработки персональных данных.
