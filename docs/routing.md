# Маршрутизация

Маршруты строит собственный движок внутри доверенного контура:
`backend/routing/`. Сторонние сервисы маршрутизации не используются.

## Зачем понадобился свой движок

Геометрию маршрута строил публичный демо-сервер OSRM, и браузер отправлял
ему точные координаты пользователя и всех точек. Получался разрыв: внешней
языковой модели мы отдаём `@HOME` вместо адреса, а координаты тем временем
уходят третьей стороне, с которой нет договора.

Теперь координаты доходят только до нашего сервера. Из `connect-src`
в политике безопасности убран последний сторонний хост.

## Почему не готовый движок

Сервер — **одно ядро и 2 ГБ**. Это определило всё остальное.

| Вариант | Почему отклонён |
|---|---|
| OSRM | Подготовка данных требует кратно больше памяти, чем весит экстракт; рантайм держит обработанный граф целиком |
| GraphHopper | JVM со своей кучей — от гигабайта только под неё |
| Valhalla | Тайлы экономны по памяти, но сборка и сам контейнер тяжелы для такой машины |
| Свой граф в типизированных массивах | Город укладывается в десятки мегабайт, запрос — единицы миллисекунд |

Городская дорожная сеть — это сотни тысяч узлов. В виде плоских целочисленных
массивов она весит два десятка мегабайт. Разворачивать ради неё отдельный
сервис на машине, где всего 2 ГБ, несоразмерно задаче.

## Как устроено

```
backend/routing/
  format.js   бинарный формат: CSR-граф в типизированных массивах
  graph.js    загрузка и привязка координат к дороге (сетчатый индекс)
  astar.js    A* и обход «один ко многим»
  osm.js      разбор выгрузки OpenStreetMap
  engine.js   публичный интерфейс: маршрут, матрица времён, кеш
```

Три решения продиктованы слабым сервером:

1. **Состояние поиска выделяется один раз** и переиспользуется между
   запросами. Вместо очистки массивов — счётчик поколений: запись считается
   своей, только если её метка совпадает с номером текущего поиска.
   Обнулять десяток мегабайт на каждый запрос дороже самого поиска.
2. **Куча — два плоских массива**, а не массив объектов. На одном ядре
   сборщик мусора конкурирует с алгоритмом за процессор.
3. **Потолок раскрытых узлов.** Запрос через полгорода упирается
   в предсказуемый предел и возвращает отказ, а не занимает ядро.

Эвристика A* — расстояние по прямой, делённое на верхнюю границу скорости,
**наблюдаемую в этом графе**. Паспортный максимум профиля (90 км/ч) давал бы
заниженную оценку в городе без скоростных дорог, и A* вырождался бы в Дейкстру:
на замере маршрут через весь город из-за этого упирался в потолок.

Матрица времён для выбора ближайшей клиники считается **одним обходом**
на всех кандидатов. Десять отдельных поисков обходили бы одну и ту же
окрестность десять раз.

## Замеры

Сетка 640×640 — 410 000 узлов, 1,6 млн рёбер. Это заведомо пессимистичный
случай: в равномерной решётке все пути равноценны и эвристике не за что
зацепиться, тогда как реальная дорожная сеть имеет выраженную иерархию.

| Показатель | Значение |
|---|---|
| Файл графа | 20 МБ |
| В памяти с индексом привязки | 22 МБ |
| Состояние поиска | 8 МБ |
| Загрузка при старте | 19 мс |
| RSS процесса целиком | ~116 МБ |

| Запрос | Медиана | p95 | Раскрыто узлов |
|---|---|---|---|
| ~1,5 км | <1 мс | <1 мс | 205 |
| ~7 км (типичный) | 1 мс | 1 мс | 4 945 |
| ~23 км (через Казань) | 23 мс | 25 мс | 94 567 |
| ~46 км (больше города) | 99 мс | 116 мс | 352 348 |
| Повтор из кеша | 0,1 мс | | |
| 10 кандидатов: матрица | 51 мс | | 187 676 |
| 10 кандидатов: по отдельности | 155 мс | | 625 136 |

Казань — примерно 25–30 км в поперечнике, поэтому рабочий потолок
это строка «~23 км»: **около 25 мс на ядро**. Типичный маршрут до
ближайшей клиники — **1 мс**.

## Сборка графа

Выгрузка делается **один раз и не на боевом сервере** — ей нужны сеть
и память, которых на слабой машине лучше не занимать.

```bash
node scripts/build-road-graph.mjs                    # Казань по умолчанию
node scripts/build-road-graph.mjs --tiles 4          # мельче тайлы, если запрос не укладывается в таймаут
node scripts/build-road-graph.mjs --endpoint https://overpass.kumi.systems/api/interpreter
node scripts/build-road-graph.mjs --input dump.json  # из готовой выгрузки, без сети
```

Скрипт сам ждёт свободный слот: спрашивает `/api/status` и выдерживает
паузу, вместо того чтобы получать `429`. Публичные зеркала Overpass —
волонтёрский ресурс, и выгрузка делается один раз, спешить некуда.

### Если Overpass отказывает

При ошибке скрипт печатает **тело ответа сервера**, а не только код.
Частые случаи:

| Код | Причина | Что делать |
|---|---|---|
| 406 | Зеркало не приняло запрос: чаще всего из-за безымянного User-Agent | Скрипт представляется сам; если повторяется — попробуйте `--endpoint` с другим зеркалом |
| 429 | Все слоты квоты заняты | Скрипт ждёт освобождения; при упорстве уменьшите `--tiles` |
| 504 | Запрос не уложился в таймаут | Увеличьте `--tiles`, чтобы тайлы стали мельче |

Обходной путь, если зеркала недоступны: выполните запрос вручную на
[overpass-turbo.eu](https://overpass-turbo.eu), экспортируйте результат
в JSON и соберите граф из файла:

```bash
node scripts/build-road-graph.mjs --input ~/Downloads/export.json
```

Запрос, который нужно выполнить, печатается командой:

```bash
node -e "import('./backend/routing/osm.js').then(m=>console.log(m.buildOverpassQuery([55.65,48.85,55.98,49.42])))"
```

Результат — `data/graph/kazan.graph`. Файл кладётся рядом с приложением;
в git он не нужен и попадает под `data/*.graph` в `.gitignore`.

Данные OpenStreetMap распространяются по лицензии **ODbL**. Собранный граф —
производное произведение, поэтому в интерфейсе требуется указание авторства:
«© участники OpenStreetMap».

## Если графа нет

Отсутствие файла — **штатный режим**, а не ошибка:

- `/api/route` отвечает `503` с кодом `routing_graph_unavailable`;
- интерфейс рисует прямые пунктирные линии между точками и помечает оценку
  приблизительной, вместо того чтобы оставить пользователя без подсказки;
- выбор ближайшей клиники переходит на расстояние по прямой — выбор
  становится грубее, но приложение работает.

## Настройка

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `ROUTING_PROVIDER` | `local` | `haversine` — всегда по прямой; `osrm` — сторонний сервер |
| `ROUTING_GRAPH_PATH` | `data/graph/kazan.graph` | путь к файлу графа |
| `ROUTING_OSRM_URL` | — | нужен только при `ROUTING_PROVIDER=osrm` |

> Включение `osrm` означает передачу координат пользователя третьей стороне.
> Это самостоятельная передача данных, и её нужно отражать в политике
> конфиденциальности. По умолчанию выключено.

## Что осталось

1. **Сжатие цепочек степени 2.** В реальной выгрузке OSM большинство узлов —
   геометрия, а не перекрёстки. Их свёртка в рёбра-полилинии уменьшила бы
   граф поиска в несколько раз. Не сделано намеренно: это меняет формат
   (нужна геометрия на ребре), а проверить на настоящих данных Казани в этой
   сессии было нечем.
2. **Двунаправленный поиск.** Сократил бы худший случай примерно вдвое.
   При текущих 25 мс на рабочем диапазоне не окупается усложнением.
3. **Пробки и время суток.** Сейчас скорость берётся из тегов OSM и
   не зависит от часа. ETA — оценка свободного потока.
4. **Повороты и запреты.** Развороты и запрещённые повороты не учитываются:
   для навигации «к какому врачу ближе» это несущественно, для пошаговой
   навигации по улицам — нет.
